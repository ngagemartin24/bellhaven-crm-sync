# Security review: Bellhaven review app (2026-11-08)

Scope: read of `src/bellhaven_sync/{app,cli,config,crm,apply}.py` and `templates/`, live probes of the test copy
`http://127.0.0.1:8775` only (8771, 8773, 8774 and railway.app never touched), in-process TestClient runs over a
modified copy of the snapshot. Nothing in the repo was changed. The probe scripts were kept outside the repo.
Limit: `app.py:303` (the line that picks the anti-forgery token) was redacted in my read, so I describe it from
behavior (probe 4 and 5 below), not from source.

## Findings

| Severity | Finding | Where | Proof | Fix |
|---|---|---|---|---|
| Medium | No Host, Origin or Referer validation anywhere. The only forgery defence is the double-submit token plus the SameSite=Strict cookie. A request under a forged Host (the DNS-rebinding shape) gets a fresh cookie, a page containing the token and the key-bearing links, and its POST is accepted. | `app.py:296-298` (no TrustedHostMiddleware/Origin check), `app.py:419-422` (`act` checks cookie==token only) | `GET / Host: attacker.example:8775` -> 200, `Set-Cookie: bh_csrf=...`; then `POST /cards/<id>/reject Host+Origin: attacker.example` with that cookie+token -> `303`, card gone from queue (probe5.py). Also `Origin: http://evil.example` + `Referer: http://evil.example/x` with valid cookie/token -> `303`; `Origin: null` -> `303`; `Host: evil.example:8775` -> `303` (probe2 T9-T11). Whether a real browser can be rebound onto a tailnet or loopback address (Chrome private-network blocks) is untested. | Add a Host allowlist (the configured bind host:port) and reject any POST whose Origin/Referer host differs from Host. |
| Medium | The CRM API key is written into page HTML for every viewer. `crm_link()` fills the same bearer key into `crm_browser_url`, and it is rendered as `href` on queue cards, the Locations table and the card header. Anyone who can load a page, with no login, reads the key (which has write power) from the page source, and it shows in the browser status bar on hover and on screen recordings. | `app.py:108-111`; `templates/_card.html:11-12`; `templates/locations.html:20` | Cookie-less `GET /` on the test copy: `href="http://crm.invalid/crm/test-token/accounts/001WR41PYNWXCAE2X4"`; `test-token` count in page = 1 (probe1, probe5 step 2). With a forged Host it is the same page. The real key on 8771 was not observed (not touched); the code path is identical. | Do not put the key in HTML: link to an app route (`/go/<account>`) that answers 302 to the vendor URL only on click, or drop the link. |
| Low | The anti-forgery token is not bound to the server. Any cookie value is accepted as the token, so whoever can set `bh_csrf` (a service on another port of the same host, an on-path attacker on plain http, a sibling subdomain) chooses cookie and token and passes the check. Cross-site protection is then SameSite=Strict alone. | `app.py:419-422`, `app.py:327-328` | `POST /cards/<id>/reject` with `Cookie: bh_csrf=attacker-chosen` and `csrf=attacker-chosen` -> `303 /?card=...` (probe2 T12). Missing/wrong/empty/header-only/JSON/text-plain/query-string tokens all -> `403` (T1-T8). | Sign the token (HMAC with a per-process secret, bound to the session id) and verify the signature, not just equality. |

The app is bound to the tailnet address, so any peer that tailnet policy lets reach `100.119.227.27:8771` can read the key (above) and approve. This matches the spec (one reviewer, private network) but `host_allowed` also admits all of 10/8, 172.16/12 and 192.168/16, which on a LAN or hotel network is not one person. | `cli.py:17-19`, `cli.py:37-45`; `ss -ltn`: 8771 listens on 100.119.227.27 only | `ss` shows no wildcard listener for any bellhaven port. | Restrict tailnet policy to the reviewer's devices; optionally narrow `PRIVATE_NETS` to loopback + 100.64/10. |
| Low | No security response headers on any page: no X-Frame-Options / CSP `frame-ancestors`, no `X-Content-Type-Options`, no `Referrer-Policy`, no `Cache-Control` (pages holding the key links can be cached and kept in history). Framing works from any same-site origin (another port on the same host); cross-site framing is blunted by SameSite=Strict. | `app.py:301-332` (response built without headers) | `GET /` response headers: only `date, server: uvicorn, content-length, content-type, set-cookie`. Same on `/history`, `/locations`, 404s (probe4). | Add a middleware setting `X-Frame-Options: DENY`, `CSP: default-src 'self'; frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. |

## Checked and fine

- State-changing POSTs: approve, reject, acknowledge, retry, check-again, discard (the only six in `app.py`). Each refuses with 403 on: no cookie and no token, cookie only, wrong token, empty cookie plus empty token, token only in query string, token only in an `X-CSRF-Token` header, JSON body, text/plain body (probe2 T1-T8). The card stayed pending with an unchanged version afterward.
- GET never changes state: GET on every POST route -> 405 (also OPTIONS and TRACE -> 405, no CORS headers); a sweep of 105 GETs left open cards, history write lines and history size identical (get_sweep.py).
- Replays: replaying an approve of an already-approved card -> 409 "Already decided", no extra write (history write lines 3 -> 3). Reject/acknowledge/retry/check/discard on a decided card -> 409. Stale, empty or missing `version` -> 409. Unknown card id -> 404 (probe3).
- Double submit: 6 parallel approves of one card -> one 303 and five 409; only that card's own writes recorded (probe3 A10). Two alternatives for one location: the second approve -> 409 (alt_probe.py).
- Actions that do not fit the state (acknowledge/retry/check/discard on a pending card) -> 409.
- Output encoding: hostile payloads (`<script>`, `"><img onerror>`, `'><svg onload>`, `{{7*7}}`) appended to every text field of every CRM account and contact and to name/administrator/phone of 35 website pages, 64 cards, then approvals and an injected CRM 500 whose message also carried the payload: 78 pages inspected (queue, each card, Locations, History, approve/failure redirects), 0 script, img or on* elements created, no raw payload substring, `{{7*7}}` stayed literal (no template injection); 42 payload ids were visible as escaped text so the test was not vacuous (xss_probe.py). No `|safe`, `Markup` or `autoescape` override in templates or `src/`.
- Query parameters `card`, `location`, `verdict` with markup, NUL and 5000-char values: 200, no markup created, no 500.
- Redirects: no `next`/return parameter exists; the only redirect target is a server-built `/?card=<id>` (303); `/?next=http://evil.example` is ignored.
- Static files: `/static/../`, `%2e%2e`, `..%2f`, `%5c`, double-encoded, `//etc/passwd` forms for `app.py`, `config.toml`, `.env`, `decisions.db` all 404; no directory listing; `/docs`, `/redoc`, `/openapi.json` 404.
- Error pages: 403/404/409 render a fixed template with an escaped message; malformed bodies (bad UTF-8, broken multipart, 5 MB field, long ids, NUL) gave 400/403/404, never a stack trace.
- `host_allowed`: 0.0.0.0, `::`, empty, 8.8.8.8, hostnames other than `localhost`, 172.15/172.32, 192.169, 100.128, 169.254, IPv4-mapped public addresses, hex/octal/short forms, whitespace and `%scope` forms are all refused; `main()` refuses before reading config, opening the db or binding (exit 2 for 0.0.0.0, `::`, 8.8.8.8). `host_allowed` is the only path: `uvicorn.run` is reached only through `main` -> `_serve`. Fail-closed oddities (Tailscale IPv6 `fd7a:...`, `::ffff:10.x`, `LOCALHOST` are refused) are safe. `localhost` is accepted without resolving it (depends on /etc/hosts; Info).
- Running servers: `ss -ltnp` shows every bellhaven/test port bound to 127.0.0.1 or 100.119.227.27; none on 0.0.0.0 or `::`.
- Key handling: the key comes only from `BELLHAVEN_CRM_TOKEN` or `.env` (`config.py:33`); `.env` is in `.gitignore` and absent from the tree; `ps` arguments for the 8771 process contain only `serve --host 100.119.227.27 --port 8771`; the key travels only as an `Authorization: Bearer` header (`crm.py:44`), never in a URL query or the request log; uvicorn runs at `log_level="warning"` so no access log carries URLs; `ledger.py` has no header/Authorization storage; `strings` on `decisions.db` + WAL found 0 hits for `Bearer`, `Authorization`, `/crm/`, `BELLHAVEN_CRM_TOKEN` (this cannot rule out the literal key, which I did not read); no `logs/` directory exists.
- Referer: every external link (website page, CRM links) carries `rel="noreferrer"`; the page has no third-party resources (fonts are local).
- Git history: `gitleaks detect` on 29 commits and on the working tree (`--no-git`): no leaks found (reports: `gitleaks-history.json`, `gitleaks-tree.json`). Caveat in the table above.
- CRM client: read-only by default (`crm.py:42,60`); `CrmError` carries the vendor's message, never the key (`crm.py:17-24`).
